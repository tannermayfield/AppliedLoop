# ADR-0002: Authentication

- **Status:** Accepted, 2026-10-05 (owner chose Better Auth with Google and GitHub OAuth)
- **Date:** 2026-10-05
- **Related:** SPEC §6 (Authentication and authorization) · SPEC_REVIEW R-17 · IMPLEMENTATION_PLAN T03

## Context

The spec leaves the auth provider UNSPECIFIED and requires it to sit behind an adapter exposing `AuthContext { userId, email?, roles }`. v1 roles are `STUDENT` and `ADMIN` only. BYU SSO is explicitly not a dependency. The pilot is small: one user, then 5–20 students.

## Options considered

| Option | For | Against |
|---|---|---|
| **Better Auth** (library; users and sessions live in our Postgres) | No third-party user store; student data stays in our database; OAuth sign-in without passwords; Next.js and Drizzle integrations | More setup than a hosted service; we own more of the security surface |
| Clerk (hosted) | Fastest route to a working sign-in; prebuilt UI | The vendor holds identity data; user rows must be synced; lock-in |
| Supabase Auth | Natural if Supabase is chosen as the database | Couples auth to the database host (ADR-0004 chose Neon instead) |
| Auth.js (NextAuth) | Widely used | Check its current maintenance status before choosing |

## Decision

Better Auth with **OAuth only** (Google and GitHub), no passwords, behind `lib/auth`, which exposes `getAuthContext(): Promise<AuthContext | null>` and `requireAuth()`. Nothing outside `lib/auth` imports the auth library.

- `users.id` is the identity key the rest of the schema references. If the library owns its own user table, either reuse its id as `users.id` or add a unique `auth_user_id`. Finalize at T03.
- Pilot gating: an optional email allow-list in the environment so only invited students can sign in. A guard, not a feature.
- Verify against current Better Auth documentation at T03. This ADR deliberately pins no API details.
- v1's repository access is a separate GitHub App (SPEC §5), not part of sign-in.

## Amendment: local development sign-in (2026-10-05)

Registering OAuth apps blocks trying the product, so development has an email-only sign-in form (`AUTH_DEV_LOGIN=1`). The password is derived from the server secret (HMAC of the email) and never typed or stored by a person. Safeguards: it is enabled only when `NODE_ENV` is not `production`; `loadEnv` **refuses to boot** a production process with it set; `pnpm build` forces it off; the server action re-checks. Production remains OAuth-only.

## Consequences

- Student data stays in our database; no extra vendor in the data path.
- Two OAuth applications to register (Google and GitHub).
- Switching later means swapping the `lib/auth` adapter and re-mapping `users`; domain code is unaffected.

## Open questions

- **Owner action before T03's live sign-in works:** register the Google and GitHub OAuth apps (localhost redirect URIs first, the deployed URL after T05). Local automated tests do not need them.
- Pilot gating: allow-list (default) or open sign-up?
